# pramana flow: stage by stage

Companion to [framework_arch.md](framework_arch.md) (what and why). This file is the
mechanical view: for each stage, what it runs, what it writes, which scripts it generates
and who reads them, and whether an LLM is involved.

Conventions used below:

- `store/` is shared across campaigns and keyed by DCP md5 or (Vivado version, threads).
  `campaigns/<name>/` (written `C/` below) belongs to one campaign.
- Every Vivado run except profile and funccheck is built by `pramana/tcl.py` and launched
  by `pramana/runner.py`: open the start checkpoint, set threads, run each step in a
  `STEP_BEGIN` block, append `route_design` if not routed, measure (timing summary, route
  status, pulse width), write a checkpoint only if WNS improved. Each run gets a directory
  with `run.tcl`, `vivado.log`, `vivado.jou`, `stdout.txt`, `timing_summary.txt`,
  `paths.tsv`, and one row in a `results.jsonl`.
- LLM calls are regular Claude Code sessions in tmux (`pramana/session.py`), or Codex
  (`codex exec --json`, headless) when the model id is `codex:<model>`, e.g.
  `codex:gpt-6.1-terra` in `llm_model` or `analysts`; resumed sessions work the same way. Each call logs
  its prompt and a response record under `C/llm/<stage>/`.
- The log for every stage is `C/pramana.log` (UTC). Each stage prints `=== name ===` and
  `=== name done in Ns ===`.

| **S4 search** | `search` | Latest `C/prune/<design>/rN.json`, `C/results.jsonl`, `C/search_state.json`, noise floor per design | Per active design per round, 8 Vivado runs from its best checkpoint: about 5 exploit (factored UCB bandit over the allowed subspace blended with the analyst's predictions, one pure bandit slot, one beam slot from the second-best state), 2 hypothesis tests interleaved with directive singles, 1 audit of a pruned-out factor. A design stops after `rounds` rounds or two rounds without a gain above its noise floor. ## Order in `pramana all`

`space` -> `profile` -> `probe` -> `baseline` -> `prune` -> `search` -> `discover` -> `confirm` -> `distill` -> `compile`.

Probe runs its own input check on the smallest design, so it no longer needs profile either. S2 baseline does not read any S1 output: the only link is that whichever of S1 and S2 runs first writes `input.json` and the other reuses it. Later stages read the input WNS through `Campaign.input_state()` from `input.json` (falling back to `profile.json` for store entries made before the input check existed). Space,
probe, profile and baseline are the framework layer (`pramana prepare`): work already in
`store/` or `specs/` is skipped, so a second campaign on the same DCPs pays nothing for them.

## Where Vivado runs

S0 probe, S1, S2, S4, S5 (through the trial runner), S6 (runs and funccheck xsim), evaluate.
At most 4 concurrent Vivado processes machine-wide (`PRAMANA_MAX_VIVADO`), 4 threads each,
gated on free memory, 4 h timeout, one retry on crash. Crashes are never counted as results.

## Where the LLM runs

S3 (analyst, critic), S4 (analyst re-prune and critic, when something changed), S5 (discovery agent),
S7 (note writer). No number in `kb.json` comes from an LLM. The analyst's influence on run
selection is weighted by its measured prediction accuracy; the critic can only remove runs,
never add them; the agent can only submit Tcl through the budgeted trial runner.
